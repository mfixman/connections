\begin{abstract}
	Connection tableau provers usually try to close one tableau before moving on to another branch of the search.
	We introduce \cop{SATResetCoP}, a variant of \cop{SATCoP} that instead treats the accumulated SAT abstraction as the main search object: it repeatedly resets the active tableau and uses the new ground clauses produced by these attempts to drive the SAT abstraction toward contradiction.
	This drives tableau provers with a SAT nucleus closer to saturation provers such as Vampire.
  We compare this against implementations of \cop{leanCoP} and \cop{SATCoP} in the same backend framework.
	\cop{SATResetCoP} solves \num{2971} TPTP problems under limits of 120 seconds and 1 million steps, an improvement of 54\% over our implementation of \cop{leanCoP} and 18\% over our improved implementation of \cop{SATCoP}.
	These results suggest that changing tableau guidance to force faster saturation of the ground SAT core improves the performance of teh prover.
\end{abstract}

\section{Introduction}

Connection tableau provers are an attractive way to solve first-order problems since its the core proof search is simple and goal-directed.

They originated from semantic tableau refutation models proposed by Evert~Beth and developed by Raymond~Smullyan\cite{semantictableaux}, which later added goal-directed guidance by Loveland\cite{modelelimination}.

Beckert and Posegga introduced \cop{leanTAP}\cite{leantap}, which showed how tableau methods could be implemented in small and swift Prolog programs that make experimentation easier.
This was the baseline used by Otten and Bibel to develop the first version of \cop{leanCoP}\cite{leancop}, which implemented a clausal connection calculus where proof search is driven by complementary literal connections.
This was later improved in \cop{leanCoP 2.0}\cite{leancopcut}, which added backtracking cuts, iterative deepening, and various other improvements. The system competed at \cop{CASC-21} on 2007\cite{casc21} and was the strongest connection-tableau style prover in the FOF division, althrough it remainder behind the leading saturation and instantiation based systems such as \cop{Vampire}.

Later tableau methods were based on \cop{leanCoP} and focused on improving the tableau guidance.
\cop{rlCoP} added a reinforcement learning component\cite{zomboriPrologTechnologyReinforcement2020a}, which can provide more expressive tableau guidance at the cost of extra work per step, while \cop{meanCoP} reduced unnecessary backtracking by separating cuts on reductions from cuts on extensions and introducing exclusive cuts\cite{meancop}.

Not all improvements to tableau methods come from restricting backtracking.
Rawson and Reger integrated a SAT solver into clausal connection-tableau systems for classical first-order logic\cite{satcop}, where the solution to the tableau does not come from tableau closure but from finding an unsatisfiable set of ground clauses at any point of the SAT solver.
This technique is very effective, and later improvements to \cop{SATCoP\textsubscript{0}} added tableau guidance from this SAT solver and put it was an effective entrant to CASC-28\cite{casc28} on 2021.

This paper explores the idea of further improving the tableau guidance with the objective of saturating the SAT core by aggressively resetting the tableau in order to maximise the amount of grounded entries added to the SAT core, with the objective of saturating it faster.
Just like the improvements in \cop{leanCoP}, \cop{meanCoP}, and \cop{SATCoP}, the improvements from this model come from further restricting backtracking.

\section{Preliminaries}

\subsection{Connection Calculus and Tableau Solving Methods}

Connection tableaux and model elimination give a goal-directed alternative to the saturation style used by provers such as \cop{Vampire}\cite{riazanovDesignImplementationVAMPIRE2002}.
Instead of repeatedly deriving clauses from a global clause set until a contradiction is found or the search space saturates\cite{bachmairResolutionTheoremProving2001,schulzPerformanceClauseSelection2016}, connection calculi try to close a tableau by connecting goal literals to complementary literals, either on the current path or in a fresh copy of an input clause\cite{connectiontableaux,ottenAdvancesConnectionBasedAutomated2017}.

The standard clausal connection tableau has three proof-building inferences\cite{connectiontableaux,ottenSyntaxConnectionProofs2023}.
\begin{description}
	\item[\cop{Start}] Choose an input clause and make its literals open goals.
	\item[\cop{Extension}] Open a branch on a clause containing a complementary literal, and add the remaining literals as new subgoals.
		This might require a substitution of variables with terms.
	\item[\cop{Reduction}] Closes the current goal against a complementary literal on the branch.
		Like the previous step, this might require adding a substitution.
\end{description}

The calculus is sound and complete when adding backtracking, but it is not confluent: a locally valid connection can bind variables in a way that prevents later branches from closing\cite{connectiontableaux}.

\subsection{Backtracking on Backtracking}

The main source of slowness on connection provers is \step{Backtracking}, since it tends to produce a set of steps that's similar to the one before the backtrack.
Subsequent improvements to this technique have focused on restricting the amount of backtracking done before a new tree is created.

\cop{leanCoP 2.0}, which adapted this style of connection tableau proving to Prolog and became the basis of a large family of provers for classical and non-classical logics\cite{leancopoverview}, added restricted backtracking as a Prolog \texttt{cut} to only run a single \step{Extension} and \step{Reduction} on each node, and backtrack immediately during each \step{Backtrack}.

It also introduced the concept of iterative deepening, where the height of each tree is capped to prioritise finding simpler solutions.
This maximum height is increased by 1 at a time each time the tree gets saturated.

This approach is sound, but incomplete.
The default implementation of \cop{leanCoP 2.0} comes with a schedule which, by default, disables cuts and maximum height after the iterative deepening saturates all trees of size 7.

Later systems kept finding ways to prevent backtracking.
\cop{meanCoP} separates cut on reductions from cut on extensions and introduces exclusive cuts, which preserve more alternatives than the inclusive cuts used by \cop{leanCoP}\cite{meancop}.
\cop{hopCoP} takes the opposite route: instead of deliberately throwing away alternatives, it learns constraints explaining why a search state is stuck, thereby reducing repeated backtracking while preserving completeness at a fixed iterative-deepening level\cite{rawsonConstraintLearningNonconfluent2026}.

\subsection{\cop{SATCoP} and Methods that use SAT Saturation in a Tableau}
\label{satcop}

SAT and SMT solvers have long been used to support first-order reasoning\cite{satcop,schulzSATInterpretation}.
For a connection prover, the useful observation is simple: every clause that appears in a tableau is an instance of an input clause.
If we ground these tableau clauses and collect them in a propositional SAT solver, then a SAT refutation of the collected ground clauses is a sound refutation of the original first-order problem.

Rawson and Reger implement this idea in \cop{SATCoP\textsubscript{0}}, a clausal connection-tableau prover based on \cop{leanCoP}\cite{satcop}.

While constructing the tableau, clauses present in the tableau are heuristically grounded and added to an incremental SAT solver.
If the SAT solver reports that the accumulated ground clauses are unsatisfiable, proof search can stop even if the first-order tableau itself has not been closed\cite{satcop}.
The remaining tableau variables must be mapped to ground terms before a clause is sent to SAT.
Variables get substituted using a heuristic created by Schulz: the most frequent constant in the conjecture is used, with a fallback to a fresh constant if no conjecture constant is available\cite{schulzSATInterpretation}.

Later modifications to \cop{SATCoP} gave it control of the tableau using results from the SAT solver.
In a later note included in the same paper, Rawson and Reger also describe a literal-selection refinement: prefer extension choices whose selected literal is assigned true by the current SAT solver assignment\cite[\S~9.1]{satcop}.

The strategy used in this paper, \cop{SATResetCoP}, pushes the ideas from \cop{SATCoP} further by resetting trees as soon as the ground SAT clause set stops growing.

\section{Research Vehicle}

\subsection{\cop{SATResetCoP} Specification}
\label{satresetcop}

We propose a new tableau prover based on \cop{SATCoP}, but guided by the goal of saturating the SAT solver rather than using the LeanCoP heuristics that attempt to close the current tableau.

Successive experimentation led to a simple strategy for achieving this: aggressively reset the tree when the SAT solver stops receiving new ground clauses.
This adds a broader set of ground clauses to the solver in less time, allowing the SAT solver to reach unsatisfiability earlier.

\cop{SATResetCoP} uses many of the properties of \cop{SATCoP} described in the original paper and in its ``Future Research'' section\cite[\S~9.1]{satcop}, but changes the tableau guidance to prioritise aggressive resets.

Just like \cop{SATCoP} and other provers, this approach is sound but incomplete.
However, we expect the speed at which it proves unsatisfiability can increase the number of problems solved within fixed time and step limits.

It might be useful to incorporate \cop{SATResetCoP} into the initial steps of a more complete schedule; this is explored in \cref{schedule}.

\subsection{Implementation Details}
\label{implementation_details}

Like \cop{SATCoP}, the implementation keeps a persistent SAT solver alongside the active tableau search.
The SAT state is not recreated during ordinary proof search.
Ground clauses accumulated in earlier tableau attempts remain available in later attempts, and new clauses are added incrementally to the same solver instance.

The SAT state is implemented using \cop{CaDiCaL}\cite{cadical20}.
A new virtual operation, \step{Reset}, clears the tableau, the current substitution, and the proof sequence, and starts a new tableau attempt with a specified depth bound.
It does not clear the persistent SAT solver: every reset starts from an empty tree, while the SAT solver keeps the ground information produced by earlier attempts.
An example of how this operation works can be seen in \cref{reset_example}.

This grows the UNSAT core shown at the bottom faster than in \cop{SATCoP}, allowing the SAT solver to reach unsatisfiability earlier. Substitutions are omitted for simplicity.}
	\label{reset_example}

The grounded clauses used by \cop{PySATCoP} and \cop{SATResetCoP} come from clauses that have appeared in the tableau, after applying the tableau substitution accumulated so far.
Start clauses are added to the SAT state when the run is initialised.
After successful \step{Extension} and \step{Reduction} steps, the implementation grounds the clauses currently present in the tableau and records the genuinely new ones, which are later flushed to the SAT solver.

The grounding scheme follows the soundness argument of \cref{satcop}: the SAT solver receives only ground instances of clauses generated by the tableau.
Ground terms are kept as they are, and variables assigned by the current tableau substitution are replaced by their assigned terms.
Only tableau variables that remain unassigned need to be replaced by a ground term.
Rawson~and~Reger follow the technique by Schulz\cite{schulzSATInterpretation} and use the most frequent constant in the conjecture, with a fresh constant as a fallback when the conjecture contains no constants\cite[\S~4.2]{satcop}.
Our Python \cop{SATCoP}-style variants use the simpler fallback-style choice throughout, mapping every remaining tableau variable to the same fresh artificial constant.
Thus \pysatcopz{}, \cop{PySATCoP}, and \cop{SATResetCoP} all use a simpler grounding scheme than the original \cop{SATCoP} implementation, while keeping the same soundness condition.

The reset policy does not affect the soundness of the SAT stopping condition.
Every clause added to the SAT solver is a ground instance of an input clause, after applying the current tableau substitution and replacing any remaining tableau variables by the grounding constant.
Therefore, if the accumulated propositional clauses are unsatisfiable, the original first-order clause set is unsatisfiable.
The cuts and resets only affect which ground instances are discovered, and hence the completeness and performance of the search, not the soundness of a SAT refutation once found.

The reset policy is the main implementation difference between \cop{SATResetCoP} and \cop{PySATCoP}.
At a dead end, the prover first asks whether the current tableau attempt produced any new ground clauses that have not yet been added to the SAT solver.
If it did, those clauses are flushed to the SAT solver and the prover resets at the same depth.
This gives the next tableau attempt the same depth bound, but a larger SAT state and a fresh randomised ordering of choices.
If the attempt did not produce any new ground clauses, the prover treats the current depth as exhausted and resets at the next depth instead of spending more steps on local backtracking.
The process stops as soon as the accumulated ground clauses become propositionally unsatisfiable.

\cop{SATResetCoP} randomises the \step{Start} and \step{Extension} steps in the same way as \cop{SATCoP}.
When starting a new tree, the implementation shuffles the possible starts and the literals inside each start clause.
When several extensions are possible from the leftmost open node, it shuffles the extension choices and the literal order inside the copied extension clause.
Reductions are not randomised in the current implementation.
The random generator is seeded, so the experiments remain reproducible.

Pseudocode for this implementation can be found in \cref{satresetcop_code}.

\begin{lstlisting}[float,floatplacement=h,caption={Pseudocode of the \cop{SATResetCoP} control policy.},label={satresetcop_code}]
def solve_tableau(start_clauses):
	solver := incremental_sat_solver()
	solver.add(ground(start_clauses))
	pending := empty_set

	max_depth := 1
	tableau := empty_tableau(max_depth)

	while solve_sat(solver) != UNSAT:
		model := current_model(solver)
		actions := legal_actions(tableau)

		if any Start, Extension, Reduction in actions:
			model_rank(a) :=
				2 if a is Start
				0 if selected_literal(a) is true in model
				1 if selected_literal(a) is unknown in model
				3 if selected_literal(a) is false in model

			next_action = argmin(actions, key = model_rank)
			tableau_step(next_action)

			if next_action is Reduction or Extension:
				pending.add(ground(tableau))

		else:
			if pending is not empty:
				solver.add_all(pending)
				pending := empty_set
				tableau := empty_tableau(max_depth)
			else:
				max_depth := max_depth + 1
				tableau := empty_tableau(max_depth)
\end{lstlisting}

As a testbed for our experiments we use the Connections Prover by Rømming et.\ al\cite{connections_2023}, which provides primitives for the implementation of connection tableau provers.
The base prover can be found in \url{https://github.com/fredrrom/connections}.


The connections prover makes it easy to implement different strategies for guiding the tableau proof.
This keeps the \cop{SATResetCoP} implementation simple, readable, and easy to evaluate.

\subsection{TPTP Benchmarking}

Along with our implementation of \cop{SATResetCoP}, the connections prover allows us to reimplement \cop{PyLeanCoP} and \cop{PySATCoP} in the same backend\cite{connections_2023}.
This provides a fairer baseline for comparison.


We run \cop{SATResetCoP}, our two connection-tableau baselines, and a simple strategy that chooses the first possible action on \num{7815} CNF problems and \num{8779} FOF problems from the Thousands of Problems for Theorem Provers (TPTP) library\cite{tptp}.
These problems cover all 50 TPTP categories containing at least one CNF or FOF problem.

The library provides a varied problem set that is a standard benchmark for first-order provers.
It also provides declared statuses for these problems, which are a useful sanity check for false unsatisfiability results.

\section{Experimental Evaluation}

\subsection{Experiment Design}

The connections prover includes \cop{PyCoP}, a simple control policy that chooses the first legal non-backtrack action at each point and resets the tree with an increased maximum height when the current tree saturates.
This serves as a baseline and sanity check.
As a second control policy we use our implementation of \cop{leanCoP}\cite{leancopcut}, \cop{PyLeanCoP}.
This is a Python version of the \cop{leanCoP} Prolog implementation, with the two recommended predicates used in the first step of the schedule by Otten\cite[\S~5.5]{leancopcut}.
\begin{description}
	\item[\texttt{cut}] Choose one extension or reduction and commit to it, similarly to Prolog's \texttt{!} operator.
	\item[\texttt{comp(7)}] The prover increases the depth bound by 1 whenever the current tree saturates, until reaching maximum height 7.
		Afterwards, the height limit is removed.
\end{description}

These simple policies tend to be very effective in tableau provers\cite{leancopoverview}.

\subsubsection{Individual Results}

\cop{SATResetCoP} considerably increases the number of problems solved by both \pysatcopz{} and \cop{PySATCoP} under the 120-second time limit, as shown in \cref{problems_solved}.

\subsubsection{Soundness Verification: Problem Satisfiability}

The TPTP library includes declared statuses for its problems\cite{tptp}.
While this does not demonstrate soundness, it provides a useful check that the strategy has not become unsound by mistake.

We make a second run of \cop{SATResetCoP} with a longer 10-minute limit, whose results can be seen in \cref{sat_proof}.
The results are consistent with what we would expect if the prover were sound, as it does not find unsatisfiability (``Solved'') in any problem marked satisfiable or countersatisfiable.
It also does not solve any unknown or open problems; while this limits the number of new discoveries, any such solutions would need to be checked closely to ensure that they were not caused by an incorrect prover.

\section{Future Work}

\subsection{Schedule}
\label{schedule}

\cop{SATResetCoP} still struggles with a significant number of problems, as seen in \cref{newly_solved_table}.
It would be worth experimenting with adding this strategy to a schedule, following the examples of Otten and Mangla\cite{leancopcut,mangla2022a}, and possibly running a different strategy or solver if no solution is found after a fixed amount of time or number of steps.

\section{Usage Example}

The repo in \url{https://github.com/mfixman/resetsatcop} contains two Python files that can be run standalone.
% \begin{description}
% 	\item[\texttt{pycop.py}] Runs a single strategy on a single problem, optionally printing every step, and reports unsatisfiability from tableau closure or from SAT core saturation.
% 	\item[\texttt{compare\_strategies.py}] Runs a sequence of strategies on a set of problems
% \end{description}

\texttt{pycop.py} gets as input a single strategy and a single \texttt{.p} file, in either FOF or CNF format.
This can be expressed as the path to this file, or a TPTP file specification; in the latter case, the file's path is expected to be inside where the main TPTP directory, which can be specified either with the \texttt{--tptp} option or with the \texttt{\$TPTP} environment variable points.

\texttt{compare\_strategies.py} can compare the result of running different strategies in a group of files.
The program takes a series of strategies and a directory or set of \texttt{.p} problems as an argument (all TPTP problems by default), and returns a CSV with solving information for each strategy/problem pair.

The program aggressively uses multiprocessing, and will try to ``fit'' each strategy/problem pair into a single processor core.
Additionally, it keep partial information of solved problems; runs of \texttt{compare\_strategies.py --name A} after the first one will retry from where the previous run ended, even if that run crashed or was killed for some reason.
