\begin{abstract}
	Connection-tableau provers typically construct closed tableaux by backtracking search.
	This gives lightweight proof procedures, but their low-memory search state leaves little derived information to reuse after a failed attempt.
	\cop{SATCoP} addresses this by retaining grounded tableau clauses in an incremental SAT solver, allowing the prover to refute the problem once the accumulated ground clauses become propositionally unsatisfiable.
	We introduce \cop{SATResetCoP}, which relies more directly on this persistent SAT state by resetting unproductive tableaux and using each new tableau to generate further ground clauses for the SAT solver.
	On TPTP, \cop{SATResetCoP} improves over our \cop{leanCoP}-style baseline by 54\% and our \cop{SATCoP}-style baseline by 18\%.
	These results suggest that changing tableau guidance to force faster saturation of the ground SAT core improves the performance of teh prover.
\end{abstract}

\section{Introduction}
Connection-tableau provers prove first-order problems by constructing closed tableaux from sound tableau-construction rules\cite{connectiontableaux}.
Implementations usually turn this construction into backtracking search over applications of those rules.
This gives a lightweight and goal-directed proof procedure, but its small search state means that failed partial tableaux leave little derived information for later attempts to reuse.

Much practical work on connection-tableau proving has therefore focused on controlling backtracking.
The line from semantic tableaux and model elimination to \cop{leanTAP} and \cop{leanCoP} showed that goal-directed tableau search could be implemented in small, effective proof procedures\cite{semantictableaux,modelelimination,leantap,leancop}.

\cop{leanCoP} uses Prolog's SLD resolution for depth-first connection-tableau search with iterative deepening, and \cop{leanCoP 2.0} obtains substantial speedups by restricting this backtracking with Prolog cuts at the cost of completeness\cite{leancopcut}.
\cop{meanCoP} refines this pruning strategy by separating cuts on reductions from cuts on extensions and by introducing exclusive cuts, which preserve more alternatives than the inclusive cuts used by \cop{leanCoP}\cite{meancop}.

\cop{SATCoP} addresses the same weakness from a different direction\cite{satcop}.
During tableau construction, it grounds encountered clauses and stores them in an incremental SAT solver.
If the accumulated ground clauses become propositionally unsatisfiable, the original first-order problem can be proved before the active tableau has closed.
We introduce \cop{SATResetCoP}, which pushes this idea further: when the active tableau stops producing new ground clauses, it is reset, while the accumulated SAT solver state is kept.
The tableau is therefore used as a generator of ground clauses, and the SAT solver becomes the persistent object from which a proof may ultimately be obtained.

We evaluate \cop{SATResetCoP} on TPTP against \cop{leanCoP}-style and \cop{SATCoP}-style baselines implemented in the same backend.
\cop{SATResetCoP} solves 54\% more problems than the \cop{leanCoP}-style baseline and 18\% more than the \cop{SATCoP}-style baseline, suggesting that once ground clauses are preserved in the SAT solver, resetting unproductive tableaux can be an effective way to generate the clauses needed for a proof.

\section{Preliminaries}

\subsection{Connection Calculus and Tableau Search}

Connection tableaux and model elimination give a goal-directed alternative to the saturation style used by provers such as \cop{Vampire}\cite{riazanovDesignImplementationVAMPIRE2002}.
Instead of deriving clauses from a global clause set until a contradiction is found\cite{bachmairResolutionTheoremProving2001,schulzPerformanceClauseSelection2016}, connection calculi try to close a tableau by connecting goal literals to complementary literals, either on the current path or in a fresh copy of an input clause\cite{connectiontableaux,ottenAdvancesConnectionBasedAutomated2017}.

The standard clausal connection tableau has three proof-building rules\cite{connectiontableaux,ottenSyntaxConnectionProofs2023}.
\begin{description}
	\item[\cop{Start}] Choose an input clause and make its literals open goals.
	\item[\cop{Extension}] Open a branch on a clause containing a complementary literal, and add the remaining literals as new subgoals.
		This may require a substitution of variables with terms.
	\item[\cop{Reduction}] Close the current goal against a complementary literal already on the current branch.
		This may also require a substitution.
\end{description}

The rules are sound, and with fair backtracking over rule applications the calculus is complete.
The calculus is not confluent: a locally sound connection can bind variables in a way that prevents later branches from closing\cite{connectiontableaux}.
Backtracking is therefore part of the operational search procedure, not a proof-building rule.

\subsection{Backtracking Control}

Backtracking lets a prover recover from locally sound choices that later prevent tableau closure.
In \cop{leanCoP}-style provers, this search is controlled mainly by iterative deepening and Prolog cuts.
Iterative deepening bounds the tableau height and raises the bound when no proof is found.
Cuts prune alternatives after selected reductions or extensions, reducing search but making the cut phase incomplete unless the surrounding schedule later explores less restricted search\cite{leancopcut}.

\cop{meanCoP} refines this pruning mechanism by separating cuts on reductions from cuts on extensions and by introducing exclusive cuts, which preserve more alternatives than the inclusive cuts used by \cop{leanCoP}\cite{meancop}.
\cop{hopCoP} takes a different route: instead of pruning alternatives directly, it learns constraints explaining why a search state is stuck, reducing repeated backtracking while preserving completeness at a fixed iterative-deepening bound\cite{rawsonConstraintLearningNonconfluent2026}.

\subsection{\cop{SATCoP} and Persistent Ground Clauses}
\label{satcop}

\cop{SATCoP} maintains an incremental SAT solver alongside tableau search\cite{satcop}.
During tableau search, clauses appearing in the tableau are heuristically grounded and added to the SAT solver.
If the accumulated ground clauses are propositionally unsatisfiable, proof search can stop even if the active first-order tableau has not closed.

The soundness condition is that every clause sent to the SAT solver must be a ground instance of a clause generated by the tableau.
Remaining tableau variables are therefore mapped to ground terms before a clause is added.
Rawson and Reger use the grounding heuristic of Schulz: choose the most frequent constant in the conjecture, falling back to a fresh constant when no conjecture constant is available\cite{schulzSATInterpretation,satcop}.

Later \cop{SATCoP} variants also use the SAT solver to guide tableau search.
Rawson and Reger describe a literal-selection refinement that prefers extension choices whose selected literal is true in the current SAT assignment\cite[\S~9.1]{satcop}.

\section{Research Vehicle}

\subsection{\cop{SATResetCoP} Specification}
\label{satresetcop}

We propose a new tableau prover based on \cop{SATCoP}, but guided by the goal of producing the ground clauses needed for a SAT refutation rather than using the \cop{leanCoP} heuristics that attempt to close the current tableau.

The resulting strategy is simple: aggressively reset the tree when the SAT solver stops receiving new ground clauses.
This adds a broader set of ground clauses to the solver in less time, allowing the SAT solver to reach unsatisfiability earlier.

\cop{SATResetCoP} uses many of the properties of \cop{SATCoP} described in the original paper and in its ``Future Research'' section\cite[\S~9.1]{satcop}, but changes the tableau guidance to prioritise aggressive resets.

Just like \cop{SATCoP} and other provers, this approach is sound but incomplete.
However, we expect the speed at which it proves unsatisfiability can increase the number of problems solved within fixed time and step limits.

% A concrete example of how \leancopc{}, \satcopc{}, and \cop{SATResetCoP} handle \cop{SYN052-1.p} can be found in \cref{diagram_syn052_1}.

Like \cop{SATCoP}, the implementation keeps a persistent SAT solver alongside the active tableau search.
The SAT state is not recreated during ordinary proof search.
Ground clauses accumulated in earlier tableau attempts remain available in later attempts, and new clauses are added incrementally to the same solver instance.

A new virtual operation, \step{Reset}, clears the tableau, the current substitution, and the proof sequence, and starts a new tableau attempt with a specified depth bound.
It does not clear the persistent SAT solver: every reset starts from an empty tree, while the SAT solver keeps the ground information produced by earlier attempts.
An example of how this operation works can be seen in \cref{reset_example}.

This accumulates the ground clauses that form the UNSAT core shown at the bottom faster than in \cop{SATCoP}, allowing the SAT solver to reach unsatisfiability earlier. The grounded clauses used by \cop{SATResetCoP} come from clauses that have appeared in the tableau, after applying the tableau substitution accumulated so far.
Start clauses are added to the SAT state when the run is initialised.
After successful \step{Extension} and \step{Reduction} steps, the implementation grounds the clauses currently present in the tableau and records the genuinely new ones, which are later flushed to the SAT solver.

The grounding scheme follows the soundness argument of \cref{satcop}: the SAT solver receives only ground instances of clauses generated by the tableau.
Ground terms are kept as they are, and variables assigned by the current tableau substitution are replaced by their assigned terms.
Only tableau variables that remain unassigned need to be replaced by a ground term.
Our Python \cop{SATCoP}-style variants use the simpler fallback-style choice throughout, mapping every remaining tableau variable to the same fresh artificial constant.
% Thus \satcopzc{}, \satcopc{}, and \cop{SATResetCoP} all use a simpler grounding scheme than the original \cop{SATCoP} implementation, while keeping the same soundness condition.

The reset policy does not affect the soundness of the SAT stopping condition.
Every clause added to the SAT solver is a ground instance of an input clause, after applying the current tableau substitution and replacing any remaining tableau variables by the grounding constant.
Therefore, if the accumulated propositional clauses are unsatisfiable, the original first-order clause set is unsatisfiable.
The cuts and resets only affect which ground instances are discovered, and hence the completeness and performance of the search, not the soundness of a SAT refutation once found.

The aggressive reset-on-backtrack policy is the main implementation difference between \cop{SATResetCoP} and \cop{SATCoP}.
At a dead end, the prover first asks whether the current tableau attempt produced any new ground clauses that have not yet been added to the SAT solver.
If it did, those clauses are flushed to the SAT solver and the prover resets at the same depth.
This gives the next tableau attempt the same depth bound, but a larger SAT state and a fresh randomised ordering of choices.
If the attempt did not produce any new ground clauses, the prover treats the current depth as exhausted and resets at the next depth instead of spending more steps on local backtracking.
The process stops as soon as the accumulated ground clauses become propositionally unsatisfiable.

\cop{SATResetCoP} randomises the \step{Start} and \step{Extension} steps in the same way as \cop{SATCoP}.
When starting a new tree, the implementation shuffles the possible starts and the literals inside each start clause.
When several extensions are possible from the leftmost open node, it shuffles the extension choices and the literal order inside the copied extension clause.

Since \cop{SATResetCoP} resets the tree aggressively, it only increases the depth bound when the accumulated ground clauses have not been updated since the last \step{Reset}.
This prevents trees from growing out of control, while still trying to maximise the set of accumulated ground clauses.

Pseudocode for this implementation can be found in \cref{satresetcop_code}.

\begin{lstlisting}[float,floatplacement=h,caption={Pseudocode of the \cop{SATResetCoP} control policy.},label={satresetcop_code}]
def solve_tableau(start_clauses):
	solver := incremental_sat_solver()
	solver.add(ground(start_clauses))
	pending := empty_set

	max_depth := 1
	tableau := empty_tableau(max_depth)

	while solve_sat(solver) != UNSAT:
		model := current_model(solver)
		actions := legal_actions(tableau)

		if any Start, Extension, Reduction in actions:
			model_rank(a) :=
				2 if a is Start
				0 if selected_literal(a) is true in model
				1 if selected_literal(a) is unknown in model
				3 if selected_literal(a) is false in model

			next_action = argmin(actions, key = model_rank)
			tableau_step(next_action)

			if next_action is Reduction or Extension:
				pending.add(ground(tableau))

		else:
			if pending is not empty:
				solver.add_all(pending)
				pending := empty_set
				tableau := empty_tableau(max_depth)
			else:
				max_depth := max_depth + 1
				tableau := empty_tableau(max_depth)
\end{lstlisting}

It might be useful to incorporate \cop{SATResetCoP} into the initial steps of a more complete schedule; this is explored in \cref{schedule}.

\subsection{Implementation and TPTP Benchmarking}

We implement \cop{SATResetCoP} and the baseline strategies \leancopc{}, \satcopzc{}, and \satcopc{} using the \cop{Connections} library\cite{connections_2023}, which provides primitives for implementing connection-tableau provers, together with the incremental SAT solver \cop{CaDiCaL}\cite{cadical20}.
The superscript \cop{C} marks our \cop{Connections}/\cop{CaDiCaL}-based reimplementations of \cop{leanCoP}, \cop{SATCoP\textsubscript{0}}, and \cop{SATCoP}.
Using a common backend makes the strategies easier to compare by keeping the tableau representation, rule applications, grounding interface, SAT interface, and step accounting fixed.

The source code for this implementation is available online,\footnote{\url{https://github.com/mfixman/resetsatcop}} and is released under the GNU Lesser General Public Licence\cite{lgpl}.

For evaluation, we run \cop{SATResetCoP}, \leancopc{}, \satcopzc{}, and \satcopc{} on \num{7815} CNF problems and \num{8779} FOF problems from the Thousands of Problems for Theorem Provers (TPTP) library\cite{tptp}.
These problems cover all 50 TPTP categories containing at least one CNF or FOF problem.

The library provides a varied problem set that is a standard benchmark for first-order provers.
It also provides declared statuses for these problems, which are a useful sanity check for false unsatisfiability results.

\section{Experimental Evaluation}

\subsection{Experiment Design}

As a \cop{leanCoP}-style baseline we use \leancopc{}\cite{leancopcut}.
This is a Python version of the \cop{leanCoP} Prolog implementation, with the two recommended predicates used in the first step of the schedule by Otten\cite[\S~5.5]{leancopcut}.
\begin{description}
	\item[\texttt{cut}] Choose one extension or reduction and commit to it, similarly to Prolog's \texttt{!} operator.
	\item[\texttt{comp(7)}] The prover increases the depth bound by 1 whenever the current tree saturates, until reaching maximum height 7.
		Afterwards, the height limit is removed.
\end{description}

These simple policies tend to be very effective in tableau provers\cite{leancopoverview}.

We add Python implementations in the connection prover of the two versions of \cop{SATCoP} presented by Rawson and Reger\cite{satcop}: \satcopzc{}, corresponding to \cop{SATCoP\textsubscript{0}}, and \satcopc{}, corresponding to the version of \cop{SATCoP} with the improvements in the ``Future Research'' section that was submitted to CASC.
These implementations are faithful to the originals, and they allow a better comparison with \cop{SATResetCoP}.

\subsubsection{Individual Results}

\cop{SATResetCoP} considerably increases the number of problems solved by both \satcopzc{} and \satcopc{} under the 120-second time limit, as shown in \cref{problems_solved}.
The main driver is that the SAT solver reaches unsatisfiability in less time and fewer steps than in the previous strategies, as seen in \cref{strategy_solved_time,strategy_solved_steps}.
For the SAT-based variants, the \num{1000000} step limit is rarely reached, and most unsolved problems hit the 120 second limit instead.

\cop{SATResetCoP} solves \num{462} more problems than \satcopc{}, with \num{206} additional CNF problems and \num{256} additional FOF problems.
Compared with \satcopzc{}, it solves \num{1100} more problems, an increase of \num{58.8}\%, and compared with \leancopc{} it solves \num{1048} more problems, an increase of \num{54.5}\%.

\subsubsection{Soundness Verification: Problem Satisfiability}

The TPTP library includes declared statuses for its problems\cite{tptp}.
While this does not demonstrate soundness, it provides a useful check that the strategy has not become unsound by mistake.

We make a second run of \cop{SATResetCoP} with a longer 10-minute limit, whose results can be seen in \cref{sat_proof}.
The results are consistent with what we would expect if the prover were sound, as it does not find unsatisfiability (``Solved'') in any problem marked satisfiable or countersatisfiable.
It also does not solve any unknown or open problems; while this limits the number of new discoveries, any such solutions would need to be checked closely to ensure that they were not caused by an incorrect prover.

\section{Conclusion}

The experiments on \cop{SATResetCoP} show that the extreme of \emph{backtracking on backtracking}, which is preventing backtracking at all and resetting the search trees instead, is a valid way to improve tableau provers.

\Cref{comparative_results} shows that, on a 1 million step and 120 second time limit, \cop{SATResetCoP} solves \num{2971} problems.
This is \num{462} more problems than \satcopc{}, an 18\% increase, and \num{1048} more problems than \leancopc{}, a 54\% increase.
Pairwise, \cop{SATResetCoP} solves \num{598} problems that \satcopc{} does not, and \num{1139} problems that \leancopc{} does not.

The improvement is not uniform across TPTP.
It is strongest in categories where useful ground clauses accumulate quickly: \cop{SATResetCoP} solves \num{672} \step{SYN} problems, \num{64} \step{SWC} problems, and \num{215} \step{SWV} problems, compared with \num{549}, \num{11}, and \num{173} for \satcopc{}.
It also improves on \step{GEO} and \step{NUM}, solving \num{293} and \num{179} problems respectively.

The newly unsolved problems show the other side of this tradeoff.
\cop{SATResetCoP} loses \num{136} problems solved by \satcopc{}, mostly in set theory, number theory, logic calculi, and common-sense reasoning.
These are cases where the SAT abstraction does not become contradictory quickly enough, and the aggressive reset policy can discard tableau branches that a less aggressive prover eventually closes.

This suggests that accumulating ground clauses is a useful objective for connection tableaux, but not a replacement for all tableau control.
The most promising direction is therefore not a single fixed reset policy, but a schedule or controller that can use aggressive resets when ground instances are informative and fall back to ordinary connection search when they are not.

\section{Future Work}

\subsection{Schedule with different provers}
\label{schedule}

\cop{SATResetCoP} still struggles with a significant number of problems, as seen in \cref{newly_solved_table}.
It would be worth experimenting with adding this strategy to a schedule, following the examples of Otten and Mangla\cite{leancopcut,mangla2022a}, and possibly running a different strategy or solver if no solution is found after a fixed amount of time or number of steps.

\subsection{Further Experiments}

The current implementation uses \cop{CaDiCaL} as its incremental SAT solver.
Future experiments should test whether the results are stable under different SAT solvers, solver restart policies, and incremental interfaces.
This matters because \cop{SATResetCoP} relies on the solver not only for the final unsatisfiability result, but also for the model information used to guide tableau extensions.

It would also be useful to vary the reset policy itself.
The present policy resets aggressively when the current tableau stops producing new ground clauses, but the newly unsolved problems suggest that some domains need longer tableau branches before the useful ground instances appear.
A broader experiment could compare fixed reset budgets, category-specific schedules, and policies that delay resets when recent SAT models still give useful literal guidance.

\subsection{CASC Submission}

\cop{SATResetCoP} will also be packaged as a CASC entrant.
This will test whether the improvements seen here survive the standard competition setting, including the official hardware, time limits, problem selection, and input requirements.
It will also make the comparison with earlier connection-tableau systems more direct, since both \cop{leanCoP} and \cop{SATCoP} have been evaluated through CASC.

Preparing a CASC version requires more than submitting the current research prototype.
The prover should expose a stable command-line interface, handle TPTP input robustly, report SZS statuses consistently, and include a reproducible installation path for the SAT backend.
This would turn the current experimental result into a system that can be compared against the broader ATP ecosystem.
