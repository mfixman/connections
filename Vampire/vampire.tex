\begin{abstract}
	Connection tableau provers usually try to close one tableau before moving on to another branch of the search.
	We introduce \cop{SATResetCoP}, a variant of \cop{SATCoP} that instead treats the accumulated SAT abstraction as the main search object: it repeatedly resets the active tableau and uses the new ground clauses produced by these attempts to drive the SAT abstraction toward contradiction.

	We compare this against implementations of \cop{leanCoP} and \cop{SATCoP} in the same backend framework.
	\cop{SATResetCoP} solves \num{2971} problems with a 120 second and 1 million step limit, an improvement of 54\% from our implementation of \cop{leanCoP} and of 18\% from our improved implementation of \cop{SATCoP}.
	These results suggest that SAT saturation is useful as tableau search guidance.
\end{abstract}

\section{Introduction}

Connection tableau provers are attractive because the core proof search is small and goal-directed.
This is especially visible in \cop{leanCoP}, where a competitive first-order prover can be implemented with very little machinery\cite{ottenLeanCoPLeanConnectionbased2003,Otten2023leanCoP20}.
The cost is that the prover has to make many local control decisions: which clause to start from, which connection to try next, when to backtrack, and when to restart.

These choices matter because connection proof search is not confluent.
A locally valid connection can bind variables in a way that makes another branch impossible to close later.
\cop{leanCoP}'s cut option shows that even a crude restriction on backtracking can make a large practical difference, although it loses completeness unless it is used inside a complete schedule\cite{ottenLeanCoP20}.

\cop{SATCoP} changes the objective slightly.
Instead of using the tableau only as a proof object that must eventually close, it also uses the tableau as a source of ground clauses for an incremental SAT solver\cite{eliminatingModels}.
Once the accumulated ground clauses are propositionally unsatisfiable, the prover can stop even if the current first-order tableau has not closed.
This suggests a different view of tableau control: a good run is not only one that closes the tableau quickly, but one that generates useful ground instances quickly.

This paper explores that view by resetting the tableau aggressively.
If the current bounded search stops adding new ground information to the SAT solver, we abandon it and start another search.
This is incomplete as a standalone proof procedure, but useful when the goal is to saturate the SAT core fast.
The rest of the paper describes the resulting prover, \cop{SATResetCoP}, and compares it against \cop{leanCoP}-style and \cop{SATCoP}-style baselines on TPTP problems.

\section{Preliminaries}

\subsection{Connection Calculus and Tableau Solving Methods}

Connection tableaux and model elimination give a goal-directed alternative to the saturation style used by provers such as \cop{Vampire}\cite{riazanovDesignImplementationVAMPIRE2002}.
Instead of deriving clauses by proving repeatedly derive clauses from a global clause set until a contradiction is found or the search space saturates\cite{bachmairResolutionTheoremProving2001,schulzPerformanceClauseSelection2016}, connection calculi instead try to close a tableau by repeatedly connecting the goal literals to complementary literals, either on the current path or in a fresh copy of an input clause\cite{letzModelEliminationConnection2001,ottenAdvancesConnectionBasedAutomated2017}.

The standard clausal connection tableau has three proof-building inferences\cite{letzModelEliminationConnection2001,ottenSyntaxConnectionProofs2023}.
\begin{description}
	\item[\cop{Start}] Choose an input clause and make its literals open goals.
	\item[\cop{Extension}] Open a branch on a clause containing a complementary literal, and add the remaining literals as new subgoals.
		This might require a substitution of variables with predicates.
	\item[\cop{Reduction}] Closes the current goal against a complementary literal on the branch.
		Like the previous step, this might require adding a substitution.
\end{description}

The calculus is sound and complete with backtracking and iterative deepening, but it is not confluent: a locally valid connection can bind variables in a way that prevents later branches from closing\cite{rawsonConstraintLearningNonconfluent2026}.

Many different types of connection tableau provers were created around the years.
\cop{leanCoP} adapted this style of connection tableau provers to Prolog and became the base of a large family of provers for classical and non-classical logics\cite{ottenLeanCoPLeanConnectionbased2003,Otten2023leanCoP20}.

\cop{leanCoP} comes with many optional predicate options.
Most critical, \cop{cut} commits a Prolog cut \texttt{(!)} after every successful \step{Reduction} and \step{Extension}.
This removes many alternative local continuations and makes the base prover incomplete, but it also converges to a solution considerably faster\cite{ottenLeanCoP20}.
Additionally, \cop{leanCoP} iteratively deepens the maximum size of the tree when the options are saturated.

To keep the prover complete, the \cop{comp(I)} option removes the maximum height restrictions and the \cop{cut} when starting a tree that would have had maximum height \cop{I}.

Later systems can be read as attempts to make this local control less crude.
\cop{meanCoP} separates cut on reductions from cut on extensions and introduces exclusive cuts, which preserve more alternatives than the inclusive cuts used by \cop{leanCoP}\cite{farberCuriouslyEffectiveBacktracking2024}.
\cop{hopCoP} takes the opposite route: instead of deliberately throwing away alternatives, they learn constraints explaining why a search state is stuck, thereby reducing repeated backtracking while preserving completeness at a fixed iterative-deepening level\cite{rawsonConstraintLearningNonconfluent2026}.

Functional connection provers and the \cop{mlCoP} and \cop{monteCoP} line reorder proof steps using learned information or Monte Carlo Tree Search\cite{farberMachineLearningGuidance2021}.
\cop{rlCoP} and \cop{plCoP} make this more explicit by treating proof search as a learning-guided control process over \cop{leanCoP}-style actions\cite{Kaliszyk2018RLTP,zomboriPrologTechnologyReinforcement2020a,zomboriRoleEntropyGuiding2021}.
The common theme is the one we use below: connection-tableau proving is naturally viewed as a sequence of small control decisions over proof actions, cuts, backtracking, and restarts.

\subsection{\cop{SATCoP} and Methods that use SAT Saturation in a Tableau}
\label{satcop}

SAT and SMT solvers have long been used to support first-order reasoning\cite{eliminatingModels,schulzSATInterpretation}.
For a connection prover, the useful observation is simple: every clause that appears in a tableau is an instance of an input clause.
If we ground these tableau clauses and collect them in a propositional SAT solver, then a SAT refutation of the collected ground clauses is a sound refutation of the original first-order problem.

Rawson and Reger implement this idea in \cop{SATCoP}, a clausal connection-tableau prover based on \cop{leanCoP}\cite{eliminatingModels}.

During backtracking search, clauses present in the tableau are heuristically grounded and added to an incremental SAT solver.
If the SAT solver reports that the accumulated ground clauses are unsatisfiable, proof search can stop even if the first-order tableau itself has not been closed\cite{eliminatingModels}.
The remaining tableau variables must be mapped to ground terms before a clause is sent to SAT.
Their implementation follows a Schulz-style heuristic: use the most frequent constant in the conjecture, and fall back to a fresh constant if no conjecture constant is available\cite[\S~4.2]{eliminatingModels,schulzSATInterpretation}.

Later modifications to \cop{SATCoP} gave it control of the tableau using results from the SAT solver.
In a later note included in the same paper, Rawson and Reger also describe a literal-selection refinement: prefer extension choices whose selected literal is true in the current SAT model\cite[\S~9.1]{eliminatingModels}.

The strategy used in this paper, \cop{SATResetCoP}, pushes the ideas from \cop{SATcoP} further by resetting trees as soon as the SAT model stops growing.

\section{Research Vehicle}

\subsection{\cop{SATResetCoP} Specification}
\label{satresetcop}

We propose implementing a new tableau prover, based on \cop{SATCoP}, but with the strategy of attempting to saturate the SAT prover rather than to close the tableau.

Successive experimentation resulted in a simple strategy for achieving this: aggressively resetting the tree when the SAT solver stops adding new SAT entries results in a larger quantity and variety of SAT statements added to the solver in a smaller amount of time, which results in reaching a SAT unsatisfiability proof earlier.

\cop{SATResetCoP} uses many of the properties of \cop{SATCoP} described in the paper and in it's ``Future Research'' section\cite[\S~9.1]{eliminatingModels}, with changes to its tableau guidance to prioritise resetting the tableau aggressively.

Just like \cop{PySATCoP}, this approach is sound.
While it is less complete than \cop{PySATCoP} and other \cop{leanCoP} variants, the speed at which it proves unsatisfiability of first-order problems can result in a larger amount of problems solved in a bounded amount of time or steps.
It might be useful to incorporate \cop{SATResetCoP} into the initial steps of a more complete schedule.

A real-world example of how \cop{PyLeanCoP}, \cop{PySATCop}, and \cop{SATResetCoP} handle a real-world problem, \cop{SYN052-1.p}, can be found in \cref{diagram_syn052_1}.

\subsection{Implementation Details}
\label{implementation_details}

Like \cop{SATCoP}, the implementation keeps a persistent SAT solver alongside the active tableau search.
The SAT state is not recreated during ordinary proof search.
Ground clauses accumulated in earlier tableau attempts remain available in later attempts, and new clauses are added incrementally to the same solver instance.

The SAT state is implemented using \cop{CaDiCaL}\cite{cadical20}.
A new virtual operation, \step{Reset}, clears the tableau, the current substitution, and the proof sequence, and starts a new tableau attempt with a specified depth bound.
It does not clear the persistent SAT solver: every reset starts from an empty tree, while the SAT solver keeps the ground information produced by earlier attempts.

The grounded clauses used by \cop{PySATCoP} and \cop{SATResetCoP} come from clauses that have appeared in the tableau, after applying the tableau substitution accumulated so far.
Start clauses are added to the SAT state when the run is initialised.
After successful \step{Extension} and \step{Reduction} steps, the implementation grounds the clauses currently present in the tableau and records the genuinely new ones, and their clauses are flushed to the SAT solver.

The grounding scheme follows the soundness argument of \cref{satcop}: the SAT solver receives only ground instances of clauses generated by the tableau.
Ground terms are kept as they are, and variables assigned by the current tableau substitution are replaced by their assigned terms.
Only tableau variables that remain unassigned need to be replaced by a ground term.
Rawson~and~Reger follow the technique by Schulz\cite{schulzSATInterpretation} and use the most frequent constant in the conjecture, with a fresh constant as a fallback when the conjecture contains no constants\cite[\S~4.2]{eliminatingModels}.
\cop{SATResetCoP} always uses this fallback-style choice, mapping every remaining tableau variable to the same fresh artificial constant.
This gives a grounding scheme that is simpler than \cop{SATCoP}, while keeping the same soundness condition.

The reset policy is the main implementation difference between \cop{SATResetCoP} and \cop{PySATCoP}.
At a dead end, the prover first asks whether the current tableau attempt produced any new ground clauses that have not yet been added to the SAT solver.
If it did, those clauses are flushed to the SAT solver and the prover resets at the same depth.
This gives the next tableau attempt the same height bound, but a larger SAT state and a fresh randomised ordering of choices.
If the attempt did not produce any new ground clauses, the prover treats the current depth as exhausted and resets at the next depth instead of spending more steps on local backtracking.
The process stops as soon as the accumulated ground clauses become propositionally unsatisfiable.

\cop{SATResetCoP} randomises the \step{Start} and \step{Extension} steps in the same way as \cop{SATCoP}.
When starting a new tree, the implementation shuffles the possible starts and the literals inside each start clause.
When several extensions are possible from the leftmost open node, it shuffles the extension choices and the literal order inside the copied extension clause.
Reductions are not randomised in the current implementation.
The random generator is seeded, so the experiments remain reproducible.

Pseudocode for this implementation can be found in \cref{satresetcop_code}.

\begin{lstlisting}[float,floatplacement=h,caption={Pseudocode of the \cop{SATResetCoP} control policy.},label={satresetcop_code}]
def solve_tableau(start_clauses):
	solver := incremental_sat_solver()
	solver.add(ground(start_clauses))
	pending := empty_set

	max_depth := 1
	tableau := empty_tableau(max_depth)

	while solve_sat(solver) != UNSAT:
		model := current_model(solver)
		actions := legal_actions(tableau)

		if any Start, Extension, Reduction in actions:
			model_rank(a) :=
				2 if a is Start
				0 if selected_literal(a) in is true in model
				1 if selected_literal(a) is unknown in model
				3 if selected_literal(a) is false in model

			next_action = argmin(actions, key = model_rank)
			tableau_step(next_action)

			if next_action is Reduction or Extension:
				pending.add(ground(tableau))

		else:
			if pending is not empty:
				solver.add_all(pending)
				pending := empty_set
				tableau := empty_tableau(max_depth)
			else:
				max_depth := max_depth + 1
				tableau := empty_tableau(max_depth)
\end{lstlisting}

\subsection{Python Implementation}

As a testbed for out experiments we use the Connections Prober by Rømming et.\ al\cite{connections_2023}, which provides an implementation of leanCoP-style provers.

The connections prover makes it easy to implement different strategies to guide the tableau proof.
This makes implementing the guidance of \cop{SATResetCoP} simple and its code easy to read and evaluate.

The source code for this implementation is present in \url{https://github.com/mfixman/resetsatcop}, and is released under the GNU Lesser General Public Licence\cite{lgpl}.

\subsection{TPTP Benchmarking}

Along with out implementation of \cop{SATResetCoP}, \cop{PyCoP} allows us to reimplement \cop{PyLeanCoP} and \cop{PySATCoP} in its own backend.
This provides a fairer baseline for comparison.

We run \cop{SATResetCoP} along with our versions of these two connection tableau strategies, along with a strategy that chooses the first possible action as control, on the \num{7815} CNF problems and \num{8779} FOF problems of all 50 categories containing at least one of these problems from the Thousands of Problems for Theorem Provers (TPTP) library\cite{tptp}.

The library provides a varied set of problems that's a standard way to prove first-order provers.
It also provides declared statuses for these problems, which are a useful sanity check for false unsatisfiability results.

\section{Experimental Evaluation}

\subsection{Experiment Design}

The connections prover provides with \cop{PyCoP}, a simple prover that chooses the first legal non-backtrack action at each point and resets the tree with an increased maximum height saturated.

As a second control policy we use our implementation of \cop{leanCoP}\cite{ottenLeanCoP20}, \cop{PyLeanCoP}.
This is a Python version of the \cop{leanCoP} Prolog implementation, with the two recommended predicates used in the first step of the schedule by Otten\cite[\S~5.5]{ottenLeanCoP20}.
\begin{description}
	\item[\texttt{cut}] Choose one choice from each extension and reduction and backtrack afterwards, in a similar way to to Prolog's \texttt{!} operator.
	\item[\texttt{comp(7)}] The prover does iterative deepening of height 1 at a time when the tree is saturated until reaching maximum height 7.
		Afterwards limits on height are restricted.
\end{description}

These kinds of simple policies tend to be very effective in tableau provers\cite{Otten2023leanCoP20}.

\subsubsection{Soundness Verification: Problem Satisfiability}

The problems in the TPTP library have a helpful specification of the satisfiability of different types of problems\cite{tptp}.
This is useful as a sanity-check: a sound solver should never ``prove'' unsatisfiability on a satisfiable problem, and their authors should be wary when proving unsatisfiability on an open or unknown problem.
While this does not demonstrate soundness, it's a check to ensure the strategy didn't become unsound by mistake.

We make a second run of \cop{SATResetCoP} with a longer 10-minute limit, whose results can be seen in \cref{sat_proof}.
These results do not show any negative results.

\section{Future Work}

\subsection{Schedule}

\cop{SATResetCoP} still struggles with a signifiant amount of problems, as seen in \cref{newly_solved_table}.
It would be worth experimenting with adding this strategy to a schedule, following the examples of Otten and Mangla\cite{ottenLeanCoP20,mangla2022a}, and possibly run a different strategy or solver if no solution was found after an amount of time or number of steps.
